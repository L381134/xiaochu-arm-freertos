# 小楚君机械手 · FreeRTOS 改造版

> 在开源机械手项目「小楚君机械手」基础上做的**固件架构重构与工程化改造**。
> 机械结构、PCB、原始固件与上位机来自原作者；本仓库的重点是把原本
> 「一个 loop 干所有事」的固件改造成多任务结构，并补齐测量与故障处理。
>
> 原项目地址：抖音 / MakerWorld 作者 **「小楚君」**
> （作者相关作品页：<https://makerworld.com.cn/zh/models/2850508-di-cheng-ben-ling-qiao-shou>）
>
> **本仓库只包含本人编写的改造代码与文档。** 原作者的 3D 模型、接线文档、
> 原始固件、上位机程序均不在此分发，需要请前往作者渠道获取。

## 这个项目解决什么问题

一句话：**原版固件在蓝牙回调里直接驱动舵机，动作会抖、会卡、断连后不恢复。**

本仓库做的事情：

1. 把「收指令」和「动舵机」拆成两个任务，用队列解耦
2. 舵机按固定 10 ms 节拍插值推进，而不是一步跳到位
3. 全工程只允许运动任务碰 I2C，从设计上消除总线竞争
4. 补上电源跌落、总线死锁两类真实故障的定位与修复

## 快速开始

### 固件

用 Arduino IDE 打开 `小楚君机械手开源/主控代码/sketch_26_7_4_rtos/sketch_26_7_4_rtos.ino`。

依赖库：`Adafruit PWM Servo Driver Library`、ESP32 BLE（Arduino-ESP32 自带）。

烧录后串口 115200，应看到：

```
=== xiaochu FreeRTOS Version ===
PCA9685 found at 0x40
motion task started, period=10ms, stack=4096 bytes
BLE ready. pulse range: 150~500, step=2.0
```

### 上位机

本人基于固件的 BLE 指令协议编写的 Kivy 控制台（`bleak` + `asyncio`），
支持手势预设与单指角度直接下发。

**该部分代码不在本仓库开源**（原委见文末「许可与致谢」）。
需要时可以提供演示视频或现场演示。

### 命令行工具（开源）

`tools/ble_cli.py` 是一个轻量替代：扫描、发指令、自动补帧头与校验、连发压测。
它的校验逻辑有离线自测，不需要板子就能跑：

```bash
python tools/ble_cli.py --selftest          # 离线验证校验算法（无需硬件）
python tools/ble_cli.py --scan              # 扫描附近的 BLE 设备
python tools/ble_cli.py --frame "S1,120"    # 自动生成 $S1,120*7D 并发送
python tools/ble_cli.py --send "servo_1=120"   # 旧格式原样发
```

## 关键设计

### 1. 为什么用队列，而不是在 BLE 回调里直接驱动舵机

BLE 的 `onWrite` 回调跑在协议栈自己的任务上下文里。在里面直接调 `pwm.setPWM()`，
意味着一次 I2C 传输（几百微秒到毫秒级）会卡住蓝牙协议栈，表现就是**连续发指令时动作排队、卡顿**。

改成「回调只解析 + 入队」，回调耗时降到微秒级，动作节奏交给独立任务，问题消失。

### 2. 为什么只有 motionTask 能碰 I2C

常见的做法是加互斥量保护总线。这里用了更彻底的办法：**单写者原则**——
全工程只允许 `motionTask` 调用 `pwm.setPWM()`，其他任务想动舵机只能往队列里投指令。

没有共享资源，就不需要锁；没有锁，就不存在优先级反转和死锁。
（换取的是所有舵机指令必须经过队列，这是一个可接受的约束。）

### 3. 为什么节拍是 10 ms

SG90 的 PWM 周期是 20 ms（50 Hz），所以 10 ms 已经比舵机能响应的更快，
再密只是浪费总线。每拍推进 2.0°，走完 180° 约 0.9 秒——这个速度看起来是"扫过去"而不是"跳过去"。

### 4. 队列满了怎么办

丢**最旧**的，保留最新的。遥控场景里用户的最新意图才有效，积压的旧指令只会让动作滞后。

### 5. 为什么给指令加帧头和校验

原版 `servo_1=120` 这类纯文本直发，`toInt()` 对残缺输入是宽容的：
尾字节丢了变成 `servo_1=1`，照样被解析成「转到 1°」并**静默执行**，
日志里只显示 `[MOTION] finger 1 -> 1°`，看不出异常。

现在支持带 XOR 校验的文本帧：`$S1,120*7D`。残帧、校验错、参数越界一律拒收并打印原因。
旧格式保留兼容，两种入口最终都转成同一个 `HandCommand`，走同一条执行路径。

格式、错误码、16 条内置用例见 [`docs/protocol.md`](docs/protocol.md)。

### 6. I2C 总线卡死后怎么救回来

SDA 是开漏共享的。主机在从机"正在吐一位数据"时复位，从机会一直把 SDA 拉低等下一个时钟，
之后所有传输全部 NACK —— 除了断电重启没有别的办法。

固件里的做法：每 5 秒探测一次总线（向 `0x40` 发空传输看有没有 ACK）。
**连续 3 次**失败（15 秒）才认为真的挂了，就地恢复：

1. 把 SDA/SCL 从 I2C 外设手里收回来，当普通 GPIO
2. 手动打 **9 个 SCL 时钟**——从机卡住时最多剩 8 位数据 + 1 位 ACK 没发完
3. 补一个 STOP 条件（SCL 为低时拉低 SDA，再把 SCL 抬高，最后放开 SDA）
4. `Wire.end()` + `Wire.begin()` 重新初始化外设，重配 PWM 频率，重写 5 路输出

恢复全程在 `motionTask` 里执行，不破坏"只有运动任务碰 I2C"的约束。

单次 NACK 不动手，是因为 I2C 偶发一次 NACK 很正常，一失败就 `Wire.end()`
反而会打断正在输出的 PWM。

> **`rc=2` 有两种完全不同的含义**：器件被拉死，或者器件压根不在总线上。
> 所以启动时那次探测结果会被锁存（`i2cPresentAtBoot`）：
> 开机就不通 → 判定为接线/供电问题，**禁用自动恢复**，并自动扫一遍总线告诉你该查哪根线。
> 这个判断来自一次真实的误判：只插 USB、没接 PCA9685 时，日志会持续刷
> `recover FAILED`，看起来像恢复算法无效。详见「踩过的坑」。

> **诚实说明**：PCA9685 是只写器件，只在 ACK 位拉低 SDA，自然卡死的概率比 MPU6050
> 这类可读器件低得多。测试用「人为把 SDA 拽低」来制造故障，验证的是恢复函数有效，
> 不代表这个故障在本硬件上高频出现。

> **验证进展（2026-10-26）**：在接上 PCA9685 的真实硬件上跑通——三步 `rc` 走成
> `0 → 2 → 0`，恢复耗时 **795 µs**（单次）。此前只在「器件不在」的失败路径上
> 观察过这段代码，成功路径这次才第一次执行。

> 更完整的取舍记录（为什么不是 4 个任务、为什么不用互斥量、10 ms 节拍怎么定的、
> 延迟预算怎么拆、XOR 的能力边界）见 [`docs/design.md`](docs/design.md)。

## 实测数据

> 全部为实测值，条件与原始数据见 `docs/measure.md`。**未用示波器交叉验证的项目已单独标注。**

| 指标 | 数值 | 测量方法 |
|---|---|---|
| 板内指令延迟（BLE 回调 → PWM 写入） | **min 1.23 ms / max 9.76 ms / avg 5.76 ms**（n=18） | 固件打时间戳，同源时钟相减 |
| 组内抖动（同一连接、固定发送节奏） | **≤ 130 µs**，漂移约 100 µs/条 | 同上，按连接会话分组统计 |
| 20 Hz 指令流下的延迟抖动 | **avg 4.24 ms，抖动仅 105 µs**（n=60） | `test=stream`，固件自产指令 |
| 队列灌爆（100 条塞进 8 深队列） | **丢弃 92 条 / 最大占用 8**，存活的是最后 8 条 | `test=flood` |
| 断连 → 回到安全位并静止 | **584 ms / 671 ms**（两次实测，取决于断开时手的姿态，最坏约 900 ms） | `test=estop` |
| motionTask 栈峰值占用 | 1680 / 4096 字节（余量 59%） | `uxTaskGetStackHighWaterMark` |
| 协议解析自测 | **16 / 16 通过** | `test=proto`，固件内置用例 |
| PWM 生效延迟（改写占空比 → 输出变化） | 待测（理论 0–20 ms） | 需示波器 / 逻辑分析仪 |
| I2C 总线卡死恢复（故障注入 → 恢复 → 复探） | **795 µs**，三步 `rc` 走通 `0 → 2 → 0`（n=1） | `test=i2c`，`micros()` 卡在恢复函数两端 |
| 5V 最低电压（五路同时动作） | 待测 | 分压电阻 + ADC 连续采样（`power_dip_test/`） |
| 连续动作复位次数 / 10 min | 待测 | 串口日志计数 |

**延迟上限的来源**：不是代码慢，是运动任务 10 ms 固定节拍——指令落在节拍窗口的位置决定了等待多久。
实测 <1.3 ms 与 >9.7 ms 都出现过，平均值 5.76 ms 正好是周期中点，与理论吻合。

**为什么 20 Hz 下抖动只有 105 µs，而手机发指令时是 8.5 ms**：
后者是手机晶振与板子晶振两个**独立时钟**的相位滑移；前者共用同一个 `SysTick`，且 50 ms 是 10 ms 的整数倍。
即延迟的不确定性来自时钟源，不是代码。

### 怎么复现

固件内置了三个实验入口，通过这些 BLE 指令触发（指令流由固件自己产生，不需要上位机配合）：

| 指令 | 实验 | 看什么 |
|---|---|---|
| `test=flood` | 100 条指令塞进 8 深队列 | `dropped`、存活指令、最终角度 |
| `test=stream` | 20 Hz × 60 条（3 秒） | `[LAT-STAT]` 的 min/max/avg、`max_depth` |
| `test=estop` | 持续开合，手动断开蓝牙 | `[ESTOP]` 断连到静止的耗时 |
| `test=proto` | 协议解析自测（16 条用例） | `[PROTO-TEST]` 的 PASS / FAIL 与总通过数 |
| `test=i2c` | 人为拉低 SDA 制造总线卡死，再调恢复函数 | 三步的 `rc`（0 → 非 0 → 0）与恢复耗时 |

## 踩过的坑

- **时间戳打晚了，测出来永远是 0。**
  **现象**：加完延迟测量代码，`[LATENCY]` 一直是 0 或负数。
  **原因**：`c.tRx = micros()` 写在了 `xQueueSend()` **之后**。队列是按值拷贝——结构体在入队那一刻就被复制走了，之后再改局部变量 `c`，队列里那份仍是 0。
  **修复**：先打时间戳、再入队、最后拉标记脚。根子是**值传递还是引用传递**没想清楚。

- **只有 2 个样本就下了结论。**
  **现象**：连续测到 6074、5940 µs，判断「BLE 连接间隔与 10 ms 节拍锁相，延迟稳定在 6 ms」。
  **结果**：样本扩到 18 条后出现 1225 µs 与 9760 µs，判断被推翻。
  **原因**：那段时间的发送节奏恰好是节拍周期的整数倍，造成了「稳定」的假象，即**采样相位效应**。
  **教训**：延迟类指标必须看 min / max / avg 三个数，单次或少量样本的「稳定」不可信。

- **调试串口本身就在延迟的统计里。**
  `applyCommand()` 里的 `Serial.printf` 发生在计时区间内，115200 波特率下一行 25 字符约耗 2.2 ms。
  所以 `RTOS_DEBUG=1` 与 `=0` 测出的延迟不在一个量级——报数据时必须写明调试开关状态。
  极端的例子是 `test=flood`：8 条指令在同一拍内执行，8 行打印把延迟撑到 34 ms，
  这个数没有意义，该实验只应该看 `dropped` 和最终角度。

- **结构体零初始化 + 漏赋字段 = 时间戳变成 0。**
  **现象**：断连时日志出现 `[LATENCY] board-side = 255395920 us`（255 秒）。
  **原因**：`onDisconnect()` 里 `HandCommand home = {};` 把 `tRx` 初始化成 0，
  之后没赋值，于是 `micros() - 0` 算出来就是开机至今的时长。
  **影响**：这个 2.5 亿的样本会被算进 `latMax` / `latSum`，之后所有汇总全部失真。
  **修复**：补 `home.tRx = micros()`；并在统计处加 `if (firstRx != 0)` 兜底，
  让「来源没打时间戳」的指令跳过统计而不是污染统计。

- **`toInt()` 太宽容，残帧会被当成合法指令执行。**
  **来源**：重写协议层时做代码 review 发现，不是线上踩到的。
  **现象推演**：`servo_1=120` 丢了尾部两个字节变成 `servo_1=1`，`toInt()` 返回 1，
  固件照样执行「转到 1°」，日志显示 `[MOTION] finger 1 -> 1°`，看不出任何异常。
  **教训**：凡是「外部输入 → 直接转数字」的路径，都要问一句「输入残缺时会怎样」。
  **修复**：帧头 + XOR 校验 + 长度约束，见 `docs/protocol.md`。

- **「恢复函数救不回来」其实是器件根本没接。**
  **现象**：D4 首次上板，只插了 USB、没接 PCA9685，日志每 5 秒刷一次
  `probe failed rc=2` → `recover FAILED (rc_after=2)`，看起来像恢复算法无效。
  **定位**：9 个时钟 + STOP + 重新打开外设是「把被咬住的总线松开」的标准流程，
  真卡死基本一次就通。连救两次都不通，说明问题不在总线状态，而在**总线上没有器件应答**。
  **教训**：`rc=2`（地址 NACK）有两种完全不同的含义——「器件被拉死」和「器件不在」。
  只看错误码分不清，必须再扫一遍总线才能定性。
  **修复**：`setup()` 里那次探测结果锁存为 `i2cPresentAtBoot`；
  开机就不通时直接判定为接线/供电问题，**禁用自动恢复**并打印 `test=scan` 的扫描结果，
  避免每 5 秒对一条「没插线的总线」做一次无意义的抢救。
  同时把单次 NACK 触发恢复改成**连续 3 次**才动手——偶发 NACK 很常见，
  一失败就 `Wire.end()` 反而会打断正在输出的 PWM。
