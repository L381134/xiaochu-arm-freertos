## D1 · 板内指令延迟

### 测的是什么

```
手机点击
   │  ① BLE 空口传输 + 连接事件调度   ← 不在本次测量范围
   ▼
onWrite 回调触发 → 打时间戳 → 入队 → 标记脚拉高   ← 起点
   │  ② 队列等待 + 任务调度 + 插值推进
   ▼
pwm.setPWM() 写入 PCA9685 → 标记脚拉低            ← 终点
   │  ③ PCA9685 等下一个 50 Hz 周期生效（0–20 ms）
   │  ④ 舵机机械响应
   ▼
手指实际开始动
```

本次测的是 **②**，即固件自身的处理延迟。

### 怎么测的

在固件里做三件事：

1. `onWrite` 回调里记录 `c.tRx = micros()`，**先打时间戳再入队**（队列按值拷贝，入队后再写时间戳无效）
2. 同一条指令结构体带着 `tRx` 传递到 `motionTask`
3. `motionTask` 取到指令后，用 `micros() - tRx` 得到差值，并翻转标记脚 `GPIO4`

`onWrite` 与 `motionTask` 跑在同一颗芯片上，`micros()` 同源，**两数相减有效**。
标记脚的作用是给示波器做交叉验证，本次测量**未接示波器**，仅使用串口输出。

> 注意：不能用手机和板子各自打时间戳相减——两者时钟不同源，差值没有物理意义。

### 原始数据

共 18 条，每条间隔约 1–3 秒，角度在 60° / 120° 之间交替（角度不变时 `Finger::run()` 会跳过 I2C 写入，不产生测量）。

按「连接会话」分组：

| 会话 | 样本（µs） | 区间 |
|---|---|---|
| A | 6074、5940 | ≈ 6.0 ms |
| B | 7286、7182、7101、7037、6922 | 7.3 → 6.9 ms |
| C | 5624 | — |
| D（改变发送节奏） | 1225、1232、9760 | 1.2 / 9.8 ms |
| E | 5041、4940、4840 | 5.0 → 4.8 ms |
| F（板子重启后） | 5987、5881、5822、5695 | 6.0 → 5.7 ms |

### 统计结果

| 指标 | 值 |
|---|---|
| 样本数 n | 18 |
| 最小值 | **1225 µs** |
| 最大值 | **9760 µs** |
| 平均值 | **5755 µs** |
| 中位数 | 5940 µs |
| 极差 | 8535 µs |
| 标准差 | 1950 µs |

### 结论

**1. 延迟不是一个随机数，而是「指令落在 10 ms 节拍窗口里的位置」。**

理论上限就是一个运动周期 10 ms：指令恰好在节拍前到达 → 几乎 0；恰好在节拍后到达 → 等满 10 ms。实测 1.2–9.8 ms，平均值 5.76 ms 落在周期中点，与理论一致。

**2. 数据呈现明显的双尺度结构。**

- **组内**（同一连接、同一发送节奏）：数值高度稳定，抖动 ≤ 130 µs，且呈**单调缓慢漂移**，每条约 80–100 µs。
- **组间**（重连、或改变发送节奏）：整组平移到另一个数值，跳变可达 8.5 ms。

这意味着延迟在短时间尺度上**可预测**，在长时间尺度上会因为相位滑移而回绕。

**3. 组内的缓慢漂移来源是两侧晶振的频率差，不是代码或人手。**

每条间隔约 1.4 s，漂移约 100 µs，换算约 **70 ppm**——落在手机晶振（±20~50 ppm）与 ESP32 晶振（±10~30 ppm）的合理偏差范围内。
换一种说法：不是「延迟在变」，是**手机与板子的时钟在相对滑动**，导致同一条指令越来越多地落在节拍周期的不同相位上。

**4. 有一处判断被数据推翻，记录在这里。**

最初只有 2 个样本（6074、5940）时，曾判断「BLE 连接间隔与 10 ms 节拍锁相，延迟稳定在 6 ms」。
样本增加到 18 条后，出现 1225 µs 与 9760 µs，说明并不存在锁定，只是那段时间的发送节奏恰好是节拍周期的整数倍，造成了「稳定」的假象。

**这是采样相位效应的典型案例：小样本会给出看似干净、实际错误的结论。**

### 这段数据的正确用法

- 报延迟要报 **min / max / avg** 三个数，只报 avg 没有意义
- 说明上限的来源：**上限由自己设计的任务节拍决定**，想降低就把节拍压到 5 ms（代价是 I2C 负载翻倍）
- 说明组内抖动很小（≤130 µs），即系统在短时间尺度上是确定性的

### 本次没测到的部分

| 项目 | 原因 | 计划 |
|---|---|---|
| PWM 生效延迟（0–20 ms） | 需要看 PCA9685 输出波形 | 有示波器 / 逻辑分析仪后补测 |
| BLE 空口延迟 | 需要手机侧与板侧同源时钟或仪器打点 | 不作为本项目指标 |
| 舵机机械响应 | 属于执行器特性 | 查 SG90 规格书，约 0.1 s/60° |

## D2 · 队列策略与断连保护

### 测的是什么

三个实验全部由固件自己产生指令流（`test=flood` / `test=stream` / `test=estop`），
不经 BLE。原因见下：

> 上位机发送的节奏会被 BLE 连接间隔打散（D1 已用 100 µs/条的漂移证明），
> 而 D2 要看的是**队列与任务调度本身**的行为，指令源必须干净。
> 代价是这条路径不含无线传输，延迟口径与 D1 一致（都从指令产生的那一刻算）。

### 实验一：flood —— 队列灌爆

100 条指令在几百微秒内全部塞进 8 深的队列。

| 指标 | 实测 | 理论 |
|---|---|---|
| 入队 100 条耗时 | **653 µs** | — |
| 因队列满被丢弃 | **92** | 100 − 8 = 92 |
| 队列历史最大占用 | **8** | 队列深度 8 |
| 存活的指令 | 第 92~99 条（167°~180°） | 最后 8 条 |
| 最终目标 | **180°** | 第 100 条 |

**结论**：存活的正好是**最后 8 条**，说明实现的是「丢最旧」，而不是「拒绝新的」。
如果是后者，存活的会是前 8 条（0°~12°），手会几乎不动——这是这两种策略最直接的区别。

> 附注：本次 `[SETTLE]` 没有打印。因为食指上一轮已停在 180°，flood 的最终目标也是 180°，
> `Finger::run()` 判定 `current == target` 直接返回，手根本没动。
> 沉降检测要求「先看到在动、再看到静止」两条都满足，所以正确地没有打印——
> 否则会报出一个毫无意义的 0 ms。

### 实验二：stream —— 20 Hz 指令流

每 50 ms 给一个新目标，从 30° 递增到 148°，共 60 条（3 秒），模拟拖动滑块。

| 指标 | 实测 |
|---|---|
| 样本数 n | 60 |
| 延迟最小值 | **4227 µs** |
| 延迟最大值 | **4332 µs** |
| 延迟平均值 | **4242 µs** |
| 抖动（max − min） | **105 µs** |
| 丢弃 / 队列最大占用 | **0 / 0** |

**结论一：20 Hz 下队列从未被占用。** 指令 50 ms 来一条，运动任务 10 ms 清空一次，
来一条走一条。8 深的队列远远过剩——**真正的瓶颈是 10 ms 节拍，不是队列容量**。

**结论二：手指始终只落后目标一个步长（2°），无累积滞后。**
`isStill()` 的判定是 `|当前位置 − 目标| <= 步长`，目标每 50 ms 只前进 2°（等于一个步长），
所以每时每刻都算「已到位」——手指在跟，不是在追。

**结论三（本次最重要的发现）：抖动从 8.5 ms 降到 105 µs，差别在时钟源。**

| 场景 | 指令时钟 vs 运动节拍时钟 | 抖动 |
|---|---|---|
| D1：手机发指令 | 手机晶振 ↔ 板子晶振（**异源**） | 8.5 ms（整个节拍周期） |
| D2：固件自产指令 | 同一个 `SysTick`（**同源**），且 50 ms 是 10 ms 的整数倍 | 105 µs（≈1/100 节拍） |

所以 D1 那个 1.2~9.8 ms 的分布，**不是代码引入的不确定性，而是两个独立时钟的相位滑移**。
同源时钟下，延迟几乎是常数。这句话是这一组实验最值钱的产出。

### 实验三：estop —— 断连保护

手指持续开合过程中，手动断开上位机蓝牙。

| 指标 | 实测 |
|---|---|
| 断连 → 五根手指全部静止（已回到张开位） | **671 ms** |

**结论**：断连后手不会僵在半紧状态，而是主动回到张开位。
671 ms 是由「断开瞬间手合得多紧」决定的——最坏情况（全握到全张）约 900 ms（90 拍 × 10 ms），
本次断开时手在行程中段，所以是 671 ms。

### 本次踩到的 bug

断连时下发的 `CMD_HOME` 结构体没有赋 `tRx`，导致 `micros() - 0` 被算成**开机至今的时长**，
日志里出现 `[LATENCY] board-side = 255395920 us`（255 秒），并且这个值会被算进
`latMax` / `latSum`，把之后所有 `[LAT-STAT]` 汇总全部带偏。

修复两处：`home.tRx = micros()`；以及在运动任务里加 `if (firstRx != 0)` 的兜底，
让「来源没打时间戳」的指令直接跳过统计而不是污染统计。

## D4 实测：I2C 总线卡死恢复耗时

**测量时间** 2026-10-26。PCA9685 已接上总线（开机打印 `PCA9685 found at 0x40`），基线可通。

**方法** `test=i2c` 分三步：先确认基线 `rc=0`；再把 SDA 拽到低电平不放（模拟从机咬住总线），
确认探测失败 `rc=2`；然后调用 `i2cBusRecover()`，最后复探。**基线不通时该测试会直接退出**，
不会做故障注入——否则事后分不清「恢复失败」和「本来就不通」。

**原始输出**

```
[I2C-TEST] start
[I2C-TEST] 1) baseline probe: rc=0 ok
[I2C-TEST] 2) SDA held low, probe: rc=2 bus broken (expected)
[I2C-TEST] 3) recovered in 795 us, probe: rc=0 ok
[I2C-TEST] pwm re-init + 5 channels rewritten
[I2C-TEST] PASS: 故障被制造出来，并被恢复函数修好
```

**结论**

- 三步 `rc` 走通 `0 → 2 → 0`，恢复函数的**成功路径**得到验证。
  此前（10-20）只观察到过失败路径：当时器件未接，探测在第一步就 NACK 退出。
- 恢复耗时 **795 µs**（单次，n=1）。

**耗时构成（按代码推算，非分段实测）**

| 阶段 | 代码 | 推算值 |
|---|---|---|
| 抢回引脚 | `pinMode` ×2 + 10 µs | 很小 |
| 9 个时钟 | 9 × (5 + 5) µs | ≈ 90 µs |
| 补 STOP | 4 × 5 µs | ≈ 20 µs |
| 外设重建 | `Wire.end()` + `Wire.begin()` + `setClock()` | **≈ 600 µs（大头）** |
| 复探确认 | 一次空传输 | 约 50–100 µs |

> 只有总的 795 µs 是实测的，各项拆分是按 `delayMicroseconds` 参数推算的。
> 但它足以说明一件事：**若要进一步压缩恢复时间，该动的是「不销毁外设、只重置状态」，
> 而不是去抠那 9 个时钟的延时**——GPIO 部分总共只占约 120 µs。

**诚实边界**

- **单次测量**，未做重复统计，不能声称分布或抖动。
- 这是**故障注入**（人工拽 SDA），证明恢复函数有效，不代表现场出现总线锁死的频率。
- 测试期间舵机应保持不动（PWM 由 PCA9685 自行产生，不受总线事务影响）；
  本次未观察到异动。
