# BLE 指令协议（带校验的文本帧）

> 目的：解决原版「纯字符串直发」在链路异常时会**静默执行错误指令**的问题。
> 兼容性：旧格式 `servo_1=120` / `fist` 仍然可用，新格式以 `$` 开头，两者共存。

---

## 1. 帧格式

```
$<body>*<HH>
```

| 字段 | 说明 |
|---|---|
| `$` | 帧头。固件看到首字节是 `$` 就按帧解析，否则走旧的文本分支 |
| `<body>` | 指令体，两种形式：`S<finger>,<angle>` 或 `G<gesture>` |
| `*` | 校验分隔符 |
| `<HH>` | 校验值，两位十六进制，大小写均可 |

**校验算法**：`body` 的每一个字节（从 `$` 之后到 `*` 之前，不含两端）按位异或。

```c
uint8_t chk = 0;
for (int i = 1; s[i] != '*'; i++) chk ^= (uint8_t)s[i];
```

### 常用帧（校验值已算好，可直接粘到输入框）

| 含义 | 帧 |
|---|---|
| 1 号手指转到 120° | `$S1,120*7D` |
| 1 号手指转到 90° | `$S1,90*47` |
| 握拳 | `$GFIST*4F` |
| 张开 | `$GFIVE*5B` |

字段约束：

- `finger` ∈ `0~4`，越界拒收
- `angle` ∈ `0~180`，越界拒收
- `gesture` 不区分大小写（`GFIST` 与 `gfist` 等价），内部统一转小写
- 手势名长度必须 `< 16` 字节

## 2. 为什么需要校验

原版解析是：

```c
if (cmd.startsWith("servo_")) {
  int finger = cmd.substring(6, eqPos).toInt();
  int angle  = constrain(cmd.substring(eqPos + 1).toInt(), 0, 180);
}
```

问题在于 **`toInt()` 对残缺输入是宽容的**：

| 实际收到 | `toInt()` 结果 | 结果 |
|---|---|---|
| `servo_1=120` | 120 | 正常 |
| `servo_1=1`（尾字节丢失） | 1 | **手指转到 1°，非法动作被静默执行** |
| `servo_1=` | 0 | **手指回到 0°** |
| `servo_x=120` | 0 | 被 `finger < 0` 拦掉，但看不出原因 |

BLE 链路在距离变化、干扰、连接参数切换时出现丢包或截断是常态。也就是说：
**一条本应转到 120° 的指令，可能因为丢了两个字节变成转到 1°**，而且日志里只显示
`[MOTION] finger 1 -> 1°`，看不出任何异常——这比直接报错危险得多。

加了 XOR 校验之后：

- 任意单字节错误 → 校验值必然改变 → 拒收
- 截断帧（缺 `*HH`）→ 结构不完整 → 拒收
- 拒收时打印具体原因，不静默

> XOR 校验只能做到「发现错误」，不能「纠正错误」，也不抗恶意构造。
> 对这个场景（短帧、低速率、只关心误动作）够用；如果要做双向可靠传输，
> 应该上 CRC-16 + 序号 + 重传。

## 3. 为什么还是文本，不用二进制

二进制帧更紧凑、解析更快，但这个项目选择了文本：

| 维度 | 文本帧 | 二进制帧 |
|---|---|---|
| 手机 App / nRF Connect 手输 | 可以 | 只能发 hex，几乎没法手打 |
| 串口日志可读性 | 直接可读 | 需要额外解包工具 |
| 体积 | 一帧 12 字节左右 | 约 6 字节 |
| 解析开销 | 几百纳秒 | 更快 |

12 字节对 BLE 的 20 字节 MTU 完全够用，**体积不是瓶颈**；而"能不能在手机上直接
敲一条指令"决定了调试效率。这里的取舍是**可测性优先于极致紧凑**。

## 4. 错误码

固件拒收时会打印 `[PROTO] reject: <原因> | raw=<原始内容>`：

| 错误码 | 触发条件 | 典型原因 |
|---|---|---|
| `no-start` | 首字节不是 `$` | 漏了帧头 |
| `no-star` | 找不到 `*` | 校验段被截断 |
| `chk-len` | `*` 后不足 2 位，或含非十六进制字符 | 手敲漏字符 |
| `chk-mismatch` | 校验值不符 | 字段改过但没重算校验 |
| `bad-cmd` | 首字母不是 `S` / `G` | 指令类型拼错 |
| `range` | 手指号或角度越界 | 参数超出 `0~4` / `0~180` |
| `format` | 字段残缺、分隔符错误、尾部有多余字节 | `S1`（缺角度）、`$S1,120*7D\r` |

`chk-mismatch` 时会额外打印正确值，方便手敲时纠正：

```
[PROTO] reject: chk-mismatch | calc should be *7D | raw=$S1,120*00
```

> 这个提示只在调试期有用。产品化时应关闭——它会告诉攻击者如何构造合法帧。

## 5. 内置自测

固件自带 16 条用例，不需要上位机也不需要硬件：

```
test=proto
```

输出（节选）：

```
[PROTO-TEST] start, 16 cases
[PROTO-TEST]  1 $S1,120*7D      expect=OK           got=OK           PASS f1/a120
[PROTO-TEST]  3 $s1,120*5D      expect=OK           got=OK           PASS f1/a120
[PROTO-TEST] 11 $S1,120*00      expect=chk-mismatch got=chk-mismatch PASS
[PROTO-TEST] 12 $S9,120*75      expect=range        got=range        PASS
[PROTO-TEST] 16 $X1,120*76      expect=bad-cmd      got=bad-cmd      PASS
[PROTO-TEST] 16/16 passed
```

用例覆盖：

| 类别 | 条数 | 覆盖点 |
|---|---|---|
| 正常帧 | 6 | 角度 / 手势 / 小写指令字 / 小写校验位 |
| 结构错误 | 4 | 缺 `$`、缺 `*`、校验位长度、非十六进制 |
| 校验错误 | 1 | 校验值不符 |
| 语义错误 | 4 | 手指号越界、角度越界、缺字段、空手势名 |
| 未知指令 | 1 | `X` 开头 |

**为什么值得在固件里写测试**：协议解析是纯逻辑，最容易在改动中悄悄破坏
（比如把 `<` 写成 `<=`，越界检查就漏一个值）。有了这 16 条用例，改完发一条
`test=proto` 就知道有没有破，成本比上板手动试低得多。

## 6. 自己算校验

改字段之后必须重算，否则会被 `chk-mismatch` 拒收。

```python
def chk(body):
    v = 0
    for c in body.encode():
        v ^= c
    return v

print("$S1,%d*%02X" % (45, chk("S1,45")))     # -> $S1,45*4F
```

或者用命令行：

```bash
python -c "import functools;b='S1,45';print('$%s*%02X'%(b,functools.reduce(lambda a,c:a^ord(c),b,0)))"
```

## 7. 尚未实现的部分

| 项 | 现状 | 说明 |
|---|---|---|
| 序号 / 去重 | 无 | 重复帧会重复执行（角度指令幂等，影响不大） |
| 应答 | 无 | 上位机不知道指令是否被接收；单向写入 |
| 双向可靠传输 | 无 | 需要 Notify 回传 + CRC-16 + 重传，超出本项目范围 |
| 帧头和转义 | 无 | 当前无 `\n` 分隔，一次 write 一帧；分片写入时会被判 `no-star` 拒收 |
