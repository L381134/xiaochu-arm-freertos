# 设计说明：这套结构为什么是这样

> 这份文档记录的是**取舍**，不是功能清单。凡是能靠"加一个任务""加一把锁"解决的地方，
> 这里都要说明为什么没有那样做。所有数字都来自实机测量，出处见 `docs/measure.md`。

---

## 0. 一句话概括

这个系统只有一个真正的硬约束：**PCA9685 以 50 Hz 输出 PWM，SG90 的机械响应在几十毫秒量级。**
所有结构选择都围绕"让 5 路 PWM 的更新时刻可预测"，而不是"把功能塞进尽可能多的任务里"。

---

## 1. 实际的执行上下文划分

| 上下文 | 谁创建 | 优先级 | 栈 | 职责 |
|---|---|---|---|---|
| BLE 回调 `onWrite` / `onDisconnect` | BLE 协议栈任务 | 高于应用任务 | 协议栈自管 | 只做解析 + 入队，**不碰 I2C、不碰舵机** |
| `motionTask` | `setup()` | 4 | 4096 B | 整个工程**唯一**调用 `pwm.setPWM()` 的地方，10 ms 固定节拍 |
| `testTask` | `setup()`（`TEST_ENABLE`） | 2 | 4096 B | 只产生测试指令流，不碰硬件 |
| `loopTask`（Arduino 默认） | core | 1 | core 默认 | 断连 300 ms 后重开广播 |

### 1.1 为什么没有做成"4 个任务"

原计划是 `ble_rx` / `motion` / `safety` / `telemetry` 四个任务，最终只保留了 `motion` 一个业务任务。理由逐条：

- **`ble_rx` 不需要**：BLE 协议栈自己就有任务，回调本来就在那个上下文里执行。
  再建一个任务，只是在"已经有一个上下文"的地方多加一次拷贝和一次上下文切换，没有任何收益。
- **`safety` 不需要**：断连检测、限位、队列满，都是几十微秒量级的判断。
  放在 10 ms 节拍里做，时间开销近似为零。而单独开一个任务，它会和 `motionTask` 共享
  `hand` 状态，就**必须**引入锁——等于用一把锁换一个任务，纯粹是负收益。
- **`telemetry` 不需要**：回传走同一条 BLE 特征，节拍里顺带发即可。

**结论：任务数量不是能力指标，同步点少才是。** 每多一个任务，就多一组竞态和一份栈开销。

- `motionTask` 优先级 4，高于 `testTask`(2) 和 `loopTask`(1)，保证 10 ms 节拍到点能及时执行。
- 但它低于 BLE 协议栈任务——所以回调必须尽快返回，这也正是"回调只入队"的另一个理由。

## 2. 单一写者：为什么不用互斥量

三个任务都可能"想动舵机"，但代码里**没有任何互斥量**，做法是：

> `hand` 与 `pwm` 只允许 `motionTask` 触碰，跨任务只通过一个队列传指令。

- 互斥量解决的是"多个任务抢同一个资源"；单一写者解决的是"根本不存在抢夺"。
- 前者是事后修补竞争，后者是事前消除竞争。后者的额外好处是：**不需要考虑锁的粒度、
  优先级继承、以及"持锁时睡眠"这类问题**。
- 代价要说清楚：**这个约束是硬约束**。将来若真有第二个任务要写 PWM，
  必须改成"向 `motionTask` 发消息"，而不能"给 `pwm` 加把锁"。
  代码里所有 I2C 操作（包括总线恢复、扫描、自测）都遵守这条：
  `testTask` 只置 `i2cTestReq` 标志，实际动作由 `motionTask` 执行。

## 3. 队列：值拷贝、定长结构体、丢旧保新

```c
struct HandCommand { CmdType type; uint8_t finger; uint8_t angle; char gesture[16]; uint32_t tRx; };
static QueueHandle_t cmdQueue;   // 深度 8，按值拷贝
```

### 3.1 为什么是 POD 而不是 `String`

`onWrite` 跑在 BLE 协议栈任务里。在里面 `new`/`delete` 会长期留下堆碎片，
碎片不会立刻报错，而是在运行几小时后以"莫名其妙分配失败"的形式出现。
用定长 `char[16]` + 逐字符解析，**全程零堆分配**。实测空闲堆在 181.4~181.6 KB 之间，
长时间运行没有单调下降。

### 3.2 为什么队列满时丢最旧的

遥控场景里，**用户最新的意图才有意义**，积压的旧指令只会让动作滞后。

`test=flood` 的实测证据（100 条指令瞬间塞入深度 8 的队列）：

| 指标 | 实测 | 说明 |
|---|---|---|
| 入队 100 条耗时 | 653 µs | 平均 6.5 µs/条，`xQueueSend` 本身几乎不耗时 |
| `dropped` | **92** | 100 − 8，一条不多一条不少 |
| `max_depth` | **8** | 队列确实被填满过 |
| 存活指令 | 第 92~99 条（167°~180°） | 证明丢的是**最旧**的，不是随机 |
| 最终目标 | **180°** | 第 100 条，最新意图一定生效 |

**反例值得记住**：如果实现成"队列满就拒绝新指令"，存活的会是**最早** 8 条（0°~12°），
手几乎不动。同样是"队列满了"，两种策略的动作结果完全相反。

### 3.3 为什么 20 Hz 下队列完全过剩

`test=stream` 实测 `dropped=0, max_depth=0`：指令 50 ms 来一条，运动任务 10 ms 清空一次，
来一条走一条。**真正的瓶颈是 10 ms 节拍，不是队列容量。**

---

## 4. 10 ms 节拍是怎么定的

| 约束 | 数值 | 影响 |
|---|---|---|
| SG90 PWM 周期 | 20 ms（50 Hz） | 占空比改动最快也要等下一个周期才体现 |
| 插值步长 | 2°/拍 | 0°→180° 需 90 拍 |
| 节拍 | 10 ms | 全行程 900 ms；每个 PWM 周期更新 2 次占空比 |
| 指令等待上限 | ≈10 ms | 指令落在节拍窗口的位置决定等待多久 |

- 若节拍取 20 ms：与 PWM 周期同频，但指令等待上限变成 20 ms，且插值分辨率变粗。
- 若节拍压到 5 ms：等待上限降到 5 ms，代价是 I2C 负载翻倍（5 路 × 每 20 ms 多一轮写），
  而 SG90 的机械响应根本跟不上——**花钱买自己用不到的东西**。
- 实测延迟分布 `min 1225 / max 9760 / avg 5755 µs`（n=18），跨度 8.5 ms，
  正好落在一个节拍内，验证了"等待上限由节拍决定"这个判断。

## 5. 延迟预算：把 100 ms 拆开看

```
手机点击
  │ ① BLE 空口（连接间隔决定，应用层不可控）
  ▼
协议栈回调 → 入队            ← 板内处理起点
  │ ② 队列等待 0~10 ms        ← 由节拍决定，可优化
  ▼
motionTask 写 PCA9685         ← 板内处理终点
  │ ③ PWM 生效 0~20 ms        ← 由 PCA9685 的 50 Hz 决定，改代码也消不掉
  ▼
舵机机械响应（几十 ms）
```

| 段落 | 实测 | 归属 |
|---|---|---|
| ② 队列等待 + 调度 + 写 I2C | **avg 4.24 ms，抖动 105 µs**（`test=stream`，n=60） | 本工程负责 |
| ② 同上，但指令来自手机 | **min 1.23 / max 9.76 ms**（n=18） | 跨度来自两枚晶振的相位差 |
| ③ PWM 生效 | 未测（理论上限 20 ms） | PCA9685 机制 |

**同一份代码，抖动 105 µs 与 8.5 ms 的差别只在指令源**：
`test=stream` 的指令和节拍共用同一个 `SysTick`，且 50 ms 是 10 ms 的整数倍；
手机发指令时是两颗独立晶振在相对滑动。
**结论：延迟的不确定性来自时钟源，不是代码质量。** 这句话比"我的延迟很低"更有信息量。

## 6. 协议：文本帧 + XOR 校验

```
$S1,120*7D
 │ └──┬──┘└┬┘
 │    │    └─ 校验：body 逐字节异或，两位十六进制
 │    └────  body：S<手指>,<角度>  或  G<手势名>
 └─────────  帧头
```

**为什么不用二进制**：串口监视器里能手敲、能肉眼读、能和日志对照。
代价是每帧 9~12 字节而非 4 字节——BLE 的 MTU 完全不是瓶颈。
**这是"可调试性优先于带宽"的选择。**

**XOR 的能力边界（必须说清楚）**：能查出单比特错误与奇数个比特翻转，
查不出偶数个比特在同一位置翻转的情况，也不做纠错——错了就整帧丢弃并计数。
帧长 ≤16 字节时这个强度够用；如果要上真正有噪声的链路，应换 CRC-16。

保留旧格式（`servo_1=120`）的原因：上位机是已打包的 exe，改协议就得重新分发；
两条分支最终都转成同一个 `HandCommand`，走同一条执行路径——
**协议层只负责把字节翻译成指令，不改变指令模型。**

## 7. 失败模式与对应动作

| 失败 | 检测方式 | 动作 | 实测 |
|---|---|---|---|
| BLE 断连 | `onDisconnect` | 下发 `CMD_HOME` 回张开位 | **584 / 671 ms** 后全部静止 |
| 队列积压 | `xQueueSend` 返回失败 | 丢最旧一条 | 100 条 → 丢 92 |
| 残帧 / 错帧 | 帧头 + 长度 + XOR | 拒收并计数 | 16 条用例全通过 |
| I2C 器件无应答 | 5 s 周期探测 | 连续 3 次失败才恢复 | 待接硬件实测 |
| 开机就没有应答 | 启动时探测 | 判定为接线/供电问题，**禁用自动恢复**并扫描总线 | 已验证 |

最后两行是同一个错误码（`rc=2`）的两种不同含义：**"器件被拉死"和"器件不在"**。
只看错误码分不清，所以启动时把结果锁存下来，并在扫描结果里告诉使用者去查线——
而不是每 5 秒对一条没插线的总线做一次无意义的抢救。

## 8. 已知限制（未做的部分）

- **写失败被吞掉了**：`Adafruit_PWMServoDriver` 的 `setPWM()` 不返回 I2C 结果，
  写失败与写成功在代码里无法区分，只能靠 5 s 周期的探测兜底。
  正确做法是自己封装 `writeReg()` 并检查返回值，让失败在第一现场暴露。
- **无帧序号**：因此无法统计"到底丢了多少帧"，只能统计"解析失败了多少帧"。
- **XOR 强度有限**，见上。
- **单总线、单器件**：没有验证多器件共存时的地址冲突与总线负载。
- **电压/电流未实测**：缺示波器与分压电阻，`5V 轨最低电压` 一栏仍是空的。
- **未覆盖高频指令流**：只测到 20 Hz，50 Hz / 100 Hz 下队列与节拍的表现未验证。
- **测试代码占用 Flash**：`TEST_ENABLE` 只是编译开关，关掉后仍会占一点空间，
  量产版本应彻底剥离。

---

## 9. 如果重做一次，会先改哪三处

1. **把 I2C 写封装成带返回值的形式**，替代直接调用库函数——让"写不进去"立刻可见。
2. **帧格式加一个序号字节**，用于统计丢帧率；这比统计"校验失败次数"更接近真实链路质量。
3. **把 `RTOS_DEBUG` 的打印从计时区间里移出去**——已经量到一行串口打印约 2.2 ms，
   它比被测对象本身还大，极端情况（`test=flood`）会把延迟撑到 34 ms。
